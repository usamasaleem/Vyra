Technical architecture

How the Sales Agent is put together.

Two processes and one datastore. A Next.js application takes the webhook and hosts the sales inbox; a worker does everything slow; PostgreSQL holds the records, the queue and the outbox. Nothing else is required to run the first pilot.

This is a proposal. None of it is built — the prototype today is a single webhook route with no durable storage, no ownership model and no handoff.

One message, arrival to reply

The order matters more than the components. Each step exists because of a specific way the naive version loses messages or says something it should not.

  1. Authenticate before trusting anythingThe webhook verifies Meta's signature against the raw, untouched body, and resolves which operator this is from the receiving phone number — never from text inside the message.
  2. Save before acknowledgingOne transaction writes the inbound event, the deduplication record and an outbox row. Success is returned only after that commits, so a crash cannot swallow a customer's message.
  3. Schedule the workA relay turns the outbox row into a job. If the queue is unavailable the row is still there, and publishing the same job twice is harmless.
  4. Load the real stateThe worker reads operator policy, who currently owns the reply, recent messages, the structured enquiry and any open approvals.
  5. Interpret, then ask for factsThe model extracts what the customer wants. Availability and rates are requested from Operations — the Sales Agent never reads or writes fleet records directly.
  6. Check the state again before sendingA short transaction rejects the draft if the customer corrected something or a salesperson took over while the model was generating. Long model calls run outside transactions; this is what makes takeover trustworthy.
  7. Dispatch through one doorChannel eligibility and ownership are checked at the moment of sending — not when the reply was queued, because a delayed job can cross the 24-hour window.
  8. Record what actually happenedProvider acceptance, delivery and read are three different things. A send whose response was lost is marked unknown rather than guessed at in either direction.

Three decisions this encodes

Each one is visible in the drawing, and each removes a category of failure rather than adding a feature.

The queue lives in PostgreSQL

The outbox table is required anyway, so the queue rides on it via graphile-worker. That removes Redis — one less service to run, one less place state can diverge, one less thing to be down at 2am.

One component talks to Meta

The dispatcher is the only sender, including for messages salespeople write. That is what makes the sending window, opt-outs and reply ownership enforceable in one place instead of three.

The model proposes, the backend authorises

Amounts, dates, expiry and booking status are rendered from validated records; the model only phrases the language around them. A hallucinated price is structurally impossible for the fields that carry money.

The worker asks Operations. It never writes fleet records.
This is the boundary the whole product rests on. Sales sends a structured request and displays the answer it gets back, with the time that answer was checked. If it could update inventory itself, nothing would stop a fluent reply from becoming an unbacked promise.

What the diagram leaves out

Deliberately, because they are states and rules rather than boxes — but they are not optional.

Tenant isolation

Row-level security covers the browser path. The worker runs on a service key and bypasses it, so every worker query needs explicit operator scoping. This is the likeliest place for a cross-operator leak, and it will not show up in testing through the interface.

Per-conversation ordering

Two rapid messages from one customer must not be processed at once. That needs a per-conversation lock or job key — a global concurrency setting does not serialise anything useful.

The Operations console

In the MVP a person answers the availability requests, in their own queue. The automated Operations Agent comes later; the request contract is the same either way.
