# Vyra application code

The specifications under [`Whatsapp Agents/`](../Whatsapp%20Agents/) remain authoritative.
This directory is the implementation of them, following the thirty-six steps in
[the build plan](../Whatsapp%20Agents/Sales%20Agent/sales%20agent%20build%20plan.md).

## Layout

Two processes and one datastore, per the recommendation in
[TECH-STACK.md](../docs/TECH-STACK.md) — not the three services in section 18.14
of the specification.

```
apps/
  inbox/        Next.js. Staff workspace AND the Meta webhook endpoint.
  worker/       graphile-worker. Conversation turns and outbound dispatch.
packages/
  contracts/    Runtime schemas and shared types.
  db/           Drizzle schema, migrations, client.
```

**Why the webhook lives in the inbox app:** a separate Fastify service is a
third deployment to configure and monitor for little gain at pilot scale. The
worker must be separate because it runs continuously.

**Why no Redis:** `graphile-worker` runs the queue on the PostgreSQL instance an
outbox table already requires. Section 18.2 explicitly permits this.

## Commands

```bash
npm install            # workspaces are linked automatically
npm run typecheck      # tsc -b across every project
npm run build          # packages, then the Next.js production build
npm run dev            # inbox on :3000
npm run dev:worker     # worker with reload
npm test               # vitest
```

`packages/*` compile to `dist/` and the apps consume the built output, so run
`npm run typecheck` after changing a package — or keep `npx tsc -b --watch`
running alongside `npm run dev`.

## Decisions made here, not in the specification

The specification names no migration tool, no error-tracking service and no
package manager. These are the choices taken, all cheap to reverse now:

| Decision | Choice | Note |
|---|---|---|
| Package manager | npm workspaces | No extra install; pnpm buys little at four packages |
| Migrations | drizzle-kit | The one gap section 6 of TECH-STACK.md flags |
| Test database | PGlite | Real PostgreSQL 18 in-process — no Docker, no local server |
| Database access | Drizzle + postgres.js | Typed queries over the same schema that generates migrations |
| Queue | graphile-worker | Replaces BullMQ/Redis |
| Error tracking | **not yet chosen** | "Unnamed means it will not exist" — still true |

Node 24 LTS is the deployment target. Local development is on Node 25.

`drizzle-kit` carries four moderate advisories through a transitive `esbuild`.
They affect an esbuild development server that never runs here, and
`npm audit fix --force` would downgrade drizzle-kit by thirteen minor versions.
Left in place deliberately.

## Testing

`packages/db/test` applies the real migrations to PGlite — PostgreSQL 18
compiled to WebAssembly, running in the test process. Schema guarantees are
therefore asserted against PostgreSQL itself rather than against the ORM's
intentions, and the suite needs no Docker daemon and no running server.

The guarantees under test today: a redelivered webhook cannot be stored twice,
two operators can independently receive the same provider event key, the same
WhatsApp number can be a contact of two different operators, a conversation
cannot reference another operator's contact, and one logical outbound intent
sends at most once.

## A note on Next.js 16

`apps/inbox/AGENTS.md` is generated by Next itself and warns that this version
differs from what an assistant's training data contains. It is accurate. Two
route options that older Next required are now wrong here:

- `export const dynamic = 'force-dynamic'` — redundant; route handlers have not
  been cached by default since v15.
- `export const runtime = 'nodejs'` — to be removed from route files; the Edge
  runtime is deprecated.

Check `node_modules/next/dist/docs/` before trusting a remembered API.

## Status

Build plan steps 1-7, less the prototype audit.

Working and tested: schema v1, the webhook verification challenge, and
`X-Hub-Signature-256` verification over the untouched request body. The GET
handshake and both signature outcomes have been exercised over real HTTP
against a running server, not only in unit tests.

**The webhook acknowledges without storing anything.** That is step 8, and until
it lands this endpoint would lose every message it accepted. Meta must not be
pointed at it. The route file says so at the handler.

**Not built:** save-before-acknowledge (8), outbox relay (9), worker task list
(10), dispatcher (11), retries (12), and all of phases 3 onward. The migration
has never been applied to a real database — there is no Supabase project yet,
which is what blocks step 8.
